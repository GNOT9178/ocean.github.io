建站部署

把博客推上线：GitHub Pages 从空仓库到可访问

我的仓库一开始只有一个 .gitignore。这篇记录从目录结构、Pages 开关、相对路径的坑，到 Cloudflare 自定义域名和 HTTPS 的完整过程。

OOcean · 2026-11-09 · 约 9 分钟

建站这件事，难的不是写页面，而是把页面变成能打开的网址。我卡了最久的地方也不是 CSS，而是「为什么推送之后访问是 404」。 这篇把整个过程按顺序记下来，包括那几个我现在想起来还挺蠢的坑。

一、先搞清楚你会拿到哪个网址

GitHub Pages 有两种站点，仓库名决定你是哪一种，这一点必须先分清：

类型仓库名必须是访问地址路径前缀
用户站点（根站点） <用户名>.github.io https://用户名.github.io/ 无
项目站点 任意其他名字 https://用户名.github.io/仓库名/ 有，且不能省略

我踩的第一个坑就在这里。仓库叫 ocean.github.io，看起来很像用户站点，但我的用户名是 GNOT9178， 两者对不上，所以它其实是项目站点，真正的地址是： 

texthttps://gnot9178.github.io/ocean.github.io/

这个结论看起来只是个「地址不一样」，实际上决定了后面所有链接的写法——这也是第四节那个坑的根源。

二、最小的可运行结构

Pages 只认一件事：仓库根目录（或指定目录）里有没有 index.html。有，就渲染；没有，就是 404。

textocean.github.io/
├── index.html          ← 必须有，首页
├── 404.html            ← 可选，自定义错误页
├── about.html
├── .nojekyll           ← 可选，见第三节
├── posts/
│   └── hello-ocean.html
└── assets/
    ├── css/style.css
    ├── js/main.js
    └── img/favicon.svg

不需要 package.json，不需要构建命令，也不需要服务器。静态文件放上去就能跑，这是 Pages 最舒服的地方。

三、打开 Pages 开关

  1. 仓库页面 → Settings（顶部导航最后一个）；
  2. 左侧边栏 → Pages；
  3. Source 选 Deploy from a branch；
  4. Branch 选 main，目录选 / (root)，点 Save；
  5. 等 1–3 分钟，刷新页面，顶部会出现「Your site is live at ...」和访问按钮。

构建进度可以在仓库的 Actions 标签或右侧 Deployments 里看。 如果部署记录显示成功但访问还是 404，先确认文件名大小写——GitHub 的服务器是 Linux，Index.html 不等于 index.html。

免费账户的两个限制

仓库必须是 Public；站点也是全网公开的。所以不要把密钥、内网地址、客户资料、扫描结果放进这个仓库——对你的专业方向来说，这条尤其重要。

四、为什么放一个 .nojekyll

默认情况下，Pages 会先跑一遍 Jekyll（Ruby 的静态站点生成器）再发布。它会忽略以下划线开头的文件和目录， 还可能改写一些内容。我们不使用 Jekyll，最简单的做法就是在仓库根目录放一个空文件，名字叫 .nojekyll， 告诉它「原样发布，别处理」。 

bash# 在仓库根目录创建空文件
$ touch .nojekyll

# Windows PowerShell 写法
PS> New-Item -ItemType File -Name .nojekyll

文件名前面有个点，资源管理器里可能看不见，用 git status 确认它真的被加进去了。

五、路径陷阱：绝对路径会 404（重点）

这一节是我花时间最多的地方。项目站点的根目录不是域名根，而是 /ocean.github.io/。所以—— 

html<!-- ❌ 错：会去请求域名根，实际地址不存在 -->
<link rel="stylesheet" href="/assets/css/style.css">

<!-- ✅ 对：相对当前文件的位置 -->
<link rel="stylesheet" href="assets/css/style.css">
<link rel="stylesheet" href="../assets/css/style.css">  <!-- 子目录里的页面 -->

表现是：HTML 能打开，但样式全丢、图片全裂、导航点不动——因为那些资源都请求到了 https://gnot9178.github.io/assets/...，而那里什么都没有。

两种修法，我选了第一种：

  • 全部用相对路径：首页写 assets/...，posts/ 里的页面写 ../assets/...。缺点是要心里有数，同一个链接在不同层级写法不同。
  • 用 <base> 标签：在 <head> 里加 <base href="/ocean.github.io/">，之后所有相对链接都从这个前缀算。缺点是把目录结构写死在了页面里，本地双击预览会失效。

相对的，如果哪天我把仓库改名成 GNOT9178.github.io（和用户名一致），它就会变成根站点，/assets/ 这种写法反而才是对的。 换仓库名之前，先把链接检查一遍。

六、推代码的两种方式

方式 A：本地 git（推荐，能写提交信息）

bash$ git add .
$ git commit -m "add: 首页与第一篇文章"
$ git push origin main

推送后等一两分钟，Pages 会自动重新构建。可以到 Actions 里看这次构建用了多久。

方式 B：网页上传（不想装 git 时够用）

  1. 仓库首页 → Add file → Upload files；
  2. 把整个文件夹拖进去，注意保持目录结构；
  3. 填提交信息，点 Commit changes。

这种方式改单篇文章很快，但一次只能传一批，多了容易漏文件。

七、自定义域名与 Cloudflare

有域名的话，Pages 也支持绑定，免费版同样能开 HTTPS。

7.1 在 GitHub 这边配

  1. Settings → Pages → Custom domain，填入域名，比如 blog.example.com；
  2. Save 之后，仓库根目录会自动生成一个 CNAME 文件，内容就是这一行域名——别删它；
  3. 等 DNS 检查通过（通常几分钟到几小时），勾上 Enforce HTTPS。

7.2 在域名解析那边配

你想用的域名记录类型值
blog.example.com（子域名，推荐）CNAMEgnot9178.github.io
example.com（根域名）A / AAAAAPEX 记录需指向 GitHub 提供的 IP，见官方文档

子域名用 CNAME 最省事，根域名麻烦一些，新手建议先用 blog. 这种子域名跑通。

7.3 Cloudflare 的两个坑

域名的 NS 托管在 Cloudflare 时，最容易出问题的是下面两点：

  • 橙色云朵（代理开启）会挡住 GitHub 的域名验证。 GitHub 需要通过 DNS 验证域名归属、并签发证书，走代理时它看到的是 Cloudflare 的 IP。 第一次配置建议先把云朵点成灰色（DNS only），等 Pages 里显示证书已签发、Enforce HTTPS 可以勾选了，再决定要不要开代理。
  • SSL/TLS 模式不要用 Flexible。Flexible 意味着「Cloudflare 到源站走 HTTP」，而 Pages 会强制跳 HTTPS， 两边互相跳转就成了重定向死循环（浏览器提示重定向次数过多）。用 Full 或 Full (strict)。

如果访问出现 522 / 526，基本就是「代理开着 + 源站配置不匹配」，先关代理排除掉这一层，再回头调。

八、强制 HTTPS 与 404 页面

Enforce HTTPS 打开后，所有 http:// 访问都会 301 到 https://。 证书没签发好之前这个选项是灰的，耐心等就行，不用反复点。

仓库根目录放一个 404.html，Pages 就会用它渲染找不到的路径——对项目站点同样有效，作用范围是整个域名。 我把它做成了一句话加两个按钮，至少不会让人直接看到 GitHub 的默认提示。

九、排错表

现象最常见原因怎么查
访问全部 404没有 index.html，或文件名大小写不对看仓库根目录文件名；Linux 区分大小写
页面能打开但没样式绝对路径写成了 /assets/...按 F12 看 Network 里 404 的请求地址
推送了但页面没变构建还没跑完，或浏览器缓存看 Actions 最新记录；Ctrl + F5 强制刷新
中文全是乱码文件不是 UTF-8 编码<meta charset="utf-8">，编辑器另存为 UTF-8
自定义域名一直 UnverifiedDNS 没生效，或开了 Cloudflare 代理nslookup 你的域名；先关代理
重定向次数过多Cloudflare SSL 模式是 Flexible改成 Full (strict)
改了仓库名后全挂站点路径前缀变了全局搜索 href="/ 和 src="/

十、本地预览

写完想马上看效果，不用等推送。任意目录下起一个静态服务器：

bash$ python -m http.server 8000
# 然后浏览器访问 http://localhost:8000/

一定要用 http:// 而不是双击文件。直接打开 file:// 时，相对路径、字体、Cookie 的行为都和线上不同， 出现「本地好好的、上线就坏」多半是这个原因。

十一、给网安方向的两条提醒

公开仓库 = 公开一切提交历史

删除文件只是「再提交一次删除」，旧内容仍然留在 git log 里，任何人都能翻出来。 所以密钥、密码、内网 IP、真实目标的扫描结果，一次都不要提交。真要放配置，用环境变量或本地文件加 .gitignore。

还有一条：你在博客里写的靶场 IP、内部笔记，都可能被搜索引擎收录。发布前花十秒问自己一句——这段内容被未来的面试官看到，是加分还是减分。
